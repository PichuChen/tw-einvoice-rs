# MIG 4.1 / F0401 model

This project models F0401 from the current Ministry of Finance MIG 4.1
specification rather than porting the older 4.0 Go/PHP SDK structures.

## Scope

The public MIG layer owns:

- the current 21-code MIG 4.1 message catalog;
- reusable lexical primitives such as BAN, invoice number, date/time, exact
  decimals, tax type/rate, buyer remark, zero-tax reason, and currency;
- the F0401 Main / Details / Amount object model;
- ProductItem cardinality of 1 through 9,999;
- deterministic XML serialization using the F0401 4.1 namespace;
- schema/lexical validation and business/usage-note validation as separate
  passes.

Transport, envelope packing, CMS signing, SFTP and PFS001 remain outside this
crate.

## Validation layers

`validate_schema_constraints()` checks constraints represented by the MIG
schema/facets, including:

- string lengths;
- RandomNumber lexical shape when present;
- ProductItem decimal total/fraction digit constraints;
- Amount decimal precision and non-negative constraints.

`validate_semantics()` checks cross-field and usage-note rules that should not
be conflated with XSD cardinality, including:

- Gregorian-calendar validity beyond the eight-digit DateType pattern;
- Seller Address requirement for F0401;
- consumer buyer-name restrictions;
- B2C RandomNumber required / business buyer RandomNumber omitted;
- PrintMark/Carrier/DonateMark consistency;
- ZeroTaxRateReason requirement when zero-rated tax is used;
- ProductItem TaxType must not use mixed-tax value 9;
- contiguous SequenceNumber ordering.

`validate()` combines both reports.

This separation is deliberate. For example, a syntactically shaped
`20230229` passes the eight-digit MIG date lexical check but fails semantic
calendar validation. Likewise, RandomNumber is optional at the XSD level but
required by the F0401 usage rule for a B2C buyer.

## Exact decimal handling

F0401 monetary/quantity values are stored as lexical decimal strings rather
than floating-point numbers. Field validation re-applies the field-specific
MIG facets even when a caller constructed a `MigDecimal` with a broader
generic precision.

Current field profiles include:

| Field | totalDigits | fractionDigits | minimum |
| --- | ---: | ---: | ---: |
| ProductItem Quantity | 20 | 7 | unrestricted |
| ProductItem UnitPrice | 20 | 7 | unrestricted |
| ProductItem Amount | 20 | 7 | unrestricted |
| SalesAmount | 20 | 7 | 0 |
| FreeTaxSalesAmount | 20 | 7 | 0 |
| ZeroTaxSalesAmount | 20 | 7 | 0 |
| TaxAmount | 20 | 0 | 0 |
| TotalAmount | 20 | 7 | 0 |
| DiscountAmount | 20 | 7 | 0 |
| OriginalCurrencyAmount | 20 | 7 | 0 |
| ExchangeRate | 13 | 5 | 0 |

## Deterministic fixture

`crates/einvoice-mig/tests/fixtures/f0401-synthetic.xml` is generated from
synthetic data and pinned byte-for-byte by the serializer unit test.

No production invoice numbers, taxpayer data, credentials, or certificates are
included.

## Known specification ambiguity

Some fields combine an XSD lexical type with narrower operational guidance.
Where the current guide is internally ambiguous, this crate keeps the
specification-level type and records stricter usage rules separately rather
than inventing a new wire type. Such cases should be resolved against the
published XSD/test platform before narrowing the public API.
